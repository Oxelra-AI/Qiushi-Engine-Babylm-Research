# span matcher review and next span discovery — SpanMatcher result review and next span-discovery experiment

## Scientific reading

span matcher construction and design should be read as a nested factorization result, not as solved raw-name binding. The successful computation has two levels. First, a context-invariant string matcher maps a verbatim candidate name and the event-side name strings into a stable candidate/other coordinate. Second, the shared relational representation uses sparse h0/h2 state anchors and a connected held-held comparison graph to orient h1/h3 state decisions. This interpretation is strengthened by the failed clean init and attention execution plan contextual-attention run: contextual name representations could fit training rows yet did not preserve held-name state, held-held comparison, or unchanged behavior.

The strongest file-backed evidence is the saved-prediction state coordinate response in `data/span_matcher_review/span_matcher_review_metrics.md` and `data/untied_and_mixed_deep_audit/untied_and_mixed_deep_audit.md`. In learned shared_trunk, graph-transfer changed rows reverse between bridge signs on every paired row: 256/256 opposite signs. Direct anchors also reverse 256/256, while unchanged rows remain same-signed 512/512 and accurate. The graph margin changes from +18.214 to -17.449, held-held closure remains 1.0, and learned and oracle state signs match on every direct, graph, unchanged, and all-changed category. The result is therefore a strong state-level reproduction of the gauge-transport fingerprint with a learned context-invariant name interface.

span matcher review and next span discovery repaired the misleading initialization reading. The span matcher construction and design printed init hashes are aggregate hashes over the condition list, so learned bs+ and bs- summaries cannot be compared directly because one run included untied and one did not. The reconstruction in `data/span_matcher_init_match_audit/init_and_match_audit.md` shows the condition-specific shared_trunk initial tensors are identical across the relevant condition-list variants: learned shared_trunk hash `9339e004bd1d2e5c226bca10b79c4f4bc5fdb529de7504cbc81514bc5a8786ff` both with and without untied present; oracle shared_trunk likewise matches. Thus the state-level sign-pair response is not explained by different starting parameters.

The matching readout needs a narrower interpretation. Untrained CharGRU self-matching is already strong because the query string is exactly one of the event names: ordinary train names average 0.945, eval names 0.950, fresh alphabetic names 0.908, and near names 0.828 across tested random seeds. span matcher construction and design’s final 1.0 matching therefore should be described as a context-invariant exact-copy equality-style interface that can be refined and can feed the relational coordinate system. It does not show that sparse state/comparison supervision taught general coreference, aliasing, morphology, pronouns, or span discovery. The `--fresh-rename` implementation in span matcher construction and design also should not be used in its current form because names such as `Xname0` and `Xname1` collapse when digits are discarded by `name_to_char_ids`.

The learned untied control arrived during span matcher review and next span discovery and is important. It fits state and comparison rows at 1.0 for both bridge signs and has perfect matching. It locally reverses direct anchors and preserves unchanged rows, but it does not show the same coordinated transport as shared_trunk. Its graph changed rows have only 0.562 opposite-sign fraction and 0.438 same-sign fraction across bridge signs; graph_same moves from 0.969 to 0.469, not from complete correct to complete sign-reversed with a coherent large-margin coordinate. Its comparison outputs are exactly bridge-sign invariant: held-held and mixed product signs stay the same with the same predictions and the same margins. This means the bridge sign did not alter the comparison coordinate in untied, whereas shared_trunk carries the bridge-selected state coordinate through the graph. The untied result is not a zero baseline; it shows that the state pathway alone can partially generalize surface regularities. But it does not replace the shared-representation mechanism.

The mixed held-seen comparison surface remains unresolved in the span matcher construction and design architecture. Learned shared_trunk has mixed accuracy 0.5 under both bridge signs; learned bs- has large absolute mixed logits around 7.875 but row truth remains at chance, indicating confident but unregistered relation-family alignment rather than uncertainty. Oracle shared_trunk also fails to reproduce causal gauge experimental design mixed behavior: bs+ reaches 0.75 only with tiny logits around 0.034, and bs- is 0.5. This shows the mixed discrepancy is not caused only by learned matcher error. It likely comes from changing the downstream interface from causal gauge experimental design vocabulary-level `<cand>/<other>` embeddings to span matcher construction and design’s match-weighted learned parameters and altered encoder path. For the present result, mixed rows should be treated as a separate comparison-registration surface, not folded into the state-level success.

## Updated principle statement

A precise supported statement is:

Finite experience becomes reusable when two transformations align. A context-invariant filler interface must first convert novel surface fillers into stable candidate-centered coordinates. Then sparse absolute anchors and graph-connected relative comparisons can orient a shared relational representation, allowing the anchor-selected coordinate to transfer to unanchored state decisions. Local fit, contextual string attention, or independent state/comparison pathways can leave internally coherent but separately oriented computations.

This statement is still controlled-harness science. The current experiment still supplies candidate strings, explicit name positions, two-participant alternatives, same/different comparison semantics, changed-vs-static routing, and a separate static scorer. It has not yet shown end-to-end entity discovery, variable-arity updating, natural-language coreference, or BabyLM-scale benefit.

## Next experiment: remove supplied entity-span positions

The next interface to remove should be event-side name position supply, because it directly tests the first level of the emerging principle. The aim is not to make the task larger, but to ask whether a context-invariant raw-string locator can create the same candidate/other coordinate without being handed `<name>` positions.

The lowest-cost sequence is as follows. First, implement deterministic raw substring scan plus hard canonicalization. Inputs are the raw event string and the two candidate strings; the code must not use supplied name spans or `<name>` markers. It should find the nonoverlapping occurrences, replace the queried candidate with `<cand>` and the other candidate with `<other>`, and then feed the original causal gauge experimental design tokenization and relational model. The first CPU result should be token-tensor identity against the supplied-coordinate causal gauge experimental design representation on all relevant state and comparison rows. No GPU run should start until this identity is recorded.

Second, if exact scan produces identical canonical tensors, run a one-seed pipeline replay for shared_trunk and untied under bridge_sign ± only to verify that the wrapper reproduces causal gauge experimental design-style state and mixed behavior. If the tensors and schedule are identical, the replay should be cheap relative to the earlier GPU work; if they are not identical, repair the canonicalizer before training. Save condition-specific initialization hashes, not aggregate hashes over condition lists.

Third, replace exact scan with a learned but context-invariant span search over raw character/byte windows, keeping the downstream hard canonicalization frozen before relational training. Report localization, canonical-token identity to exact scan, bridge-sign paired state response, held-held closure, unchanged stability, and mixed held-seen behavior separately. Use valid alphabetic fresh-renaming and near-name sets; include digit-aware encoding only if digit names are used. A frozen exact scanner and a frozen learned scanner will isolate the filler-interface level from the relational level more cleanly than span matcher construction and design’s soft match-weighted embedding path.

Fourth, include the matched negative control from clean init and attention execution plan: a contextual locator that can fit training examples but may fail held identities. This will connect the new experiment to the evidence that context-entangled matching is not enough.

The decisive readouts for the next step should include row-level state coordinates, comparison products, direct-anchor response, h1/h3 graph response, held-held comparison closure, unchanged/static stability, mixed held-seen registration, and the actual span/canonicalization records. If exact scan restores causal gauge experimental design mixed behavior while learned scan preserves it, then supplied positions were not load-bearing once context-invariant string location is available. If exact scan restores state but mixed remains weak, the discrepancy lies deeper in the relational/mixed surface. If learned scan localizes correctly but state transport fails, the canonicalization or relational sharing is disrupted. If learned scan fails on held or near names, the first-level interface remains the bottleneck.
